# Week 8 — Sprint 3 Summary

## Overview

Week 8 was the third sprint for the **Cardiac Patient Monitoring System**.

The focus of Sprint 3 was improving database access efficiency and making performance decisions based on measurable evidence. The work started by investigating generated SQL and query counts, then moved to focused query optimization, Redis caching, cache invalidation, and database indexing.

Instead of treating performance as a general impression such as “the API feels faster,” the sprint used database-query behavior and recorded profiling results as evidence. Each improvement was connected to a real endpoint and a real application need.

The main progression during the week was:

```text
Query Investigation
        ↓
N+1 Review and Query Baseline
        ↓
Projection and Read Optimization
        ↓
Redis Caching and Invalidation
        ↓
Composite Database Index
        ↓
Sprint Review and Retrospective
```

---

# Sprint 3 Goal

The goal of Sprint 3 was to improve database access efficiency and keep API query behavior predictable as the amount of data grows.

The sprint focused on:

* Measuring actual EF Core SQL queries instead of assuming query behavior.
* Checking important list endpoints for N+1 query patterns.
* Using projection and `AsNoTracking()` where they improve read operations.
* Reducing repeated database reads with Redis caching.
* Invalidating cached data after write operations.
* Adding an index that matches a real application query pattern.
* Demonstrating performance work with before/after evidence.

The key principle used throughout the sprint was:

```text
Measure actual behavior
        ↓
Identify a real improvement opportunity
        ↓
Apply a focused change
        ↓
Test and document the result
```

# Day 1 — Sprint Planning & N+1 Investigation

Day 1 established the performance baseline for the sprint. EF Core SQL logging was enabled and realistic development data was used to inspect the SQL generated by important endpoints.

The test database included a useful development dataset, including Patients, Doctors, Vital Signs, Appointments, Medical Records, Medications, and Patient Medications. This made it possible to check whether query count increased with the number of returned records.

The tested endpoints showed predictable query behavior:

| Endpoint | Database Queries | N+1 Detected |
| --- | ---: | --- |
| `GET /api/patients` | 2 | No |
| `GET /api/appointments` | 2 | No |
| `GET /api/vitalsigns` | 1 | No |

No genuine N+1 query pattern was found in the tested endpoints. This was documented as a valid result; no artificial performance problem was introduced just to produce an N+1 fix.

The conclusion from Day 1 was that the selected endpoints already used set-based queries with predictable database round trips. This baseline remains useful for future regression checks.

# Day 2 — Query Optimization & Projection

Day 2 continued the query review and improved the `GET /api/patientmedications` endpoint.

The endpoint did not have an N+1 problem, but returning the full entity graph caused a JSON object-cycle during serialization. The endpoint was changed to use projection and `AsNoTracking()`.

| Before | After |
| --- | --- |
| Full entity graph returned | Only required response fields selected |
| JSON object-cycle error | Clean `HTTP 200 OK` response |
| 1 SQL query | 1 SQL query |

The improvement was in query shape, entity materialization, and API response safety—not a reduction in query count.

This showed that query optimization is not limited to reducing the number of SQL commands. Selecting only the needed fields can produce a cleaner and safer API response while avoiding unnecessary entity loading.

# Day 3 — Redis Caching

Day 3 introduced Redis distributed caching for the medication catalog endpoint:

```http
GET /api/medications
```

The cache-aside pattern was implemented:

```text
GET /api/medications
        ↓
Check Redis
   ↓          ↓
Hit         Miss
↓             ↓
Return     Query SQL Server
cached          ↓
data        Store in Redis
                 ↓
             Return response
```

The medication catalog was selected because it is read frequently and changes less often than live patient data.

The implementation uses the Redis-backed `IDistributedCache` abstraction, so the application can use distributed caching without putting Redis-specific client logic throughout the controller.

## Cache Invalidation

The cache entry uses the key:

```text
medications:all
```

After a medication create, update, or delete operation, the application removes this cache key. The next GET request then reads current data from SQL Server and rebuilds the cache.

The cache also has a 10-minute absolute expiration. Expiration is a safety boundary, while immediate invalidation after writes is the main consistency strategy.

Testing confirmed that:

* The first GET was a cache miss and executed a medication SQL query.
* Repeated GET requests were cache hits and did not execute another medication SQL query.
* A medication update invalidated the cache.
* The next GET returned the updated data and rebuilt the cache.

This confirms the complete cache lifecycle:

```text
First request
      ↓
Cache miss and database read
      ↓
Store medication catalog in Redis
      ↓
Repeated request uses cache
      ↓
Medication write removes cache entry
      ↓
Next request reads fresh database data
```

# Day 4 — Database Indexing & Performance Profiling

Day 4 focused on a real query pattern in the appointments endpoint:

```http
GET /api/appointments?status=Scheduled
```

The query filters appointments using both `PatientId` and `Status`, so a composite index was added:

```text
IX_Appointments_PatientId_Status
```

| Measurement | Recorded Query Time |
| --- | ---: |
| Before composite index | 54ms |
| After composite index | 18ms |
| Improvement | ~66.7% |

The result was recorded in the local development environment using the same request conditions before and after the migration.

The index was added through EF Core Fluent API and a database migration. The work replaced the previous single-column `PatientId` index with an index matching the actual combined filter pattern, avoiding unnecessary duplicate indexing.

* A documented query-count baseline for important endpoints.

# Sprint Retrospective

## What Went Well

* Performance work was based on SQL logs, endpoint tests, and measured evidence.
* The sprint did not create an artificial N+1 problem; the actual query behavior was documented instead.
* Redis caching was implemented with a tested invalidation strategy.
* The composite index produced a measurable local improvement for the appointments query.

## What Could Be Improved

* Record formal cache miss and cache hit response times earlier in the testing process.
* Convert manual performance checks into automated tests where practical.

## Concrete Sprint 4 Action

Add an automated regression test that verifies the medication cache is invalidated after a write operation and that the next GET request returns current data.

This turns a manual cache-consistency check from Sprint 3 into a permanent safeguard for future changes.
